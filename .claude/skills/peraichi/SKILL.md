# peraichi：図入りの説明ペライチ HTML

コードを書く前に「何がどう変わるか」を、画面イメージと概念図で見せるための HTML を作る。
文章だけの説明だと認識がずれやすいので、図で先に合意するのが目的。

## 方針
- **凝らない・雑でよい。説明内容がしっかりしていること**が最優先。トークン節約のため、装飾・アニメ・JS は入れない。
- 1 ファイル完結（外部 CSS / JS / 画像なし）。図は inline SVG。
- デザインは `assets/template.html` の CSS をそのまま使う。**CSS は書き換えず**、`<style>` ごとコピーする。
- 出力先：プロジェクトに設計文書用のフォルダ（`docs/` など）があればそこ、無ければ作業ディレクトリ直下。ファイル名は `<課題番号や機能名>-design.html`（設計）／`-review.html`（レビュー）。既に同種のファイルがあれば命名を合わせる。
- 作ったら、ファイルのパスだけ伝える。HTML の中身をチャットに再掲しない（トークンの無駄）。
- 言語はユーザーの言葉に合わせる（テンプレートの見出しは日本語。英語で頼まれたら英語に直す）。

## 手順
1. **調べる**：依頼に関係する既存コードと、あれば仕様・要件の文書、`CLAUDE.md` などのプロジェクトの決まりを読む。推測で書かない。仕様が曖昧・矛盾なら、HTML に書く前に質問する。
2. **種類を決める**：下の「設計イメージ」か「レビュー」。両方頼まれたら 1 つの HTML にまとめてよい。
3. `assets/template.html` を土台に書く。図の部品は `references/snippets.md` からコピーして調整する。
4. 書いたら、SVG のはみ出し・文字の重なりがないか自分で軽く見直す（座標を手書きするので崩れやすい）。必要ならブラウザで開いて確認。

## 設計イメージ（コード変更前）の構成
1. **ゴールと状態**：冒頭 2〜3 行。何のためか。状態は「案／確定」。
2. **画面イメージ**（画面が変わるとき）：SVG のワイヤー。変わる所を `fill="#e8f1fd"` などで目立たせ、新規は `← 新規` と注記。
3. **概念図**（構造・データの流れが変わるとき）：箱と矢印の SVG。「いま」と「変更後」を並べると差が伝わる。
4. **対応表・変更点**：どのファイル／クラスが、いま何で、どう変わるか（`table`）。
5. **決めたいこと**：未決事項は `.q`（黄色ボックス）に書き、推奨は `.rec`（橙）で示す。選択肢ごとの利点・欠点を 1 行ずつ。
6. **リスクと対策**。

要らない節は省く。画面が変わらないなら画面イメージは出さない。

## レビューの構成
1. **結論**：先頭に「実装に進める／直してから進める／要相談」を 1 行。
2. **確認した範囲**：読んだ既存コード・文書を列挙（ファイルパス）。
3. **概念図**：既存実装と、今回の変更の関係。問題の箇所に赤（`#b33`）で印を付ける。
4. **問題一覧**（`table`）：# ／ 重大度 ／ 何が問題か（根拠となるコード位置 `file:line`）／ どう解決するか。
   - 「問題あり」には必ず**具体的な解決策**を付ける。解決の概念図（修正後の形）も、問題が構造に関わるなら付ける。
   - 問題なしの観点も 1 行で書く（`.ok`）。何を見て問題なしと判断したか分かるように。
5. **決めたいこと**：解決策が複数あるときは `.q` で選択肢と推奨。

## 守ること
- 事実と推測を分ける。コードで確認したことだけ断定し、推測は「要確認」と書く。
- プロジェクトの `CLAUDE.md` や仕様に「実装しない」「触らない」と書かれた事項に反する案・図を描かない。
- 機密になりうるもの（認証情報、個人情報、ログの本文など）を図や表に引用しない。
