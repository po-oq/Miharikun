# impl-plan：実装計画（md と図解 HTML の対）

要件が決まったあと、コードを書く前に「どう分けて、どの順で、何に気をつけて作るか」を文書にする。
実装するのも、レビューするのも、別のセッション（別のモデル）かもしれない。
**この計画だけ読めば、迷わずに実装・レビューできる**ことが目的。

## 前提（足りなければ先にやる）
- 要件が確定している：仕様の正となる文書（要件定義・仕様書・Issue の本文など）があり、設計の未決事項に回答がある。未決なら計画に入らず、先に聞く。
- Issue 管理を使っているなら、この作業の Issue がある（コミットの `Refs #N` / `Fixes #N` に使う）。無ければ作るか利用者に聞く。
- 仕様の文書に作業の区切り（フェーズ・マイルストーンなど）の欄があるなら、この機能の分を足してから計画を書く。

## 手順
1. **調べる**（推測で書かない）
   - 仕様の該当箇所、設計の資料、プロジェクトの決まり（`CLAUDE.md`・`AGENTS.md`・`CONTRIBUTING.md`・引き継ぎメモなど、あるもの）。
   - **変更・流用する実コードを実際に読む**：クラス・関数・イベント・設定・組み立て（起動時の初期化や依存の注入）。計画に書く名前は、実在するものか、新規と明記したものだけ。
   - 似た既存の計画があれば、書き方・粒度を合わせる。いまのテスト件数も控える（「減らさない」の基準）。
2. **迷いやすい所を探す**（計画の価値の大半はここ）。コードを読みながら、次の観点で「実装者がつまずく所」を拾い、決めごと（7 章）にする：
   - 起動・初期化のタイミング（遅延して始まる処理、まだ準備できていない状態で呼ばれる経路）
   - 共有するもの（同じ部品・接続・ファイル・設定を 2 か所から使う）
   - 自分の書き込みが自分の監視・通知に返ってくる、外での変更と編集中の衝突
   - 文字コード・改行・パスの大文字小文字・区切り文字・タイムゾーンの違い
   - 失敗の経路（保存できない・ファイルが無い・権限・通信の失敗）で、入力やデータを失わないか
   - 画面があるなら：要素の重なり・フォーカス・キー操作の衝突
   - 状態があるものは、**状態の表（操作 → 結果）と状態遷移の図**にする（テストの行にそのまま使える）
3. **分ける**：フェーズ → コミット（`3-1` のように番号）。仕様の側に番号があれば合わせる。基本の並び：
   - **ロジック（画面・外部に依存しない部分。テスト先行）** → **挙動を変えない共通化（必要なら単独のフェーズ。品質ゲート付き）** → **利用側（画面・API・CLI など）** → **仕上げ（README・リリース手順・仕様の進捗の更新）**
   - 各コミットの行に「内容」と「テスト／確認」を必ず書く。確認は、何をどう見れば完了か分かる粒度で。
   - 共通化・移し替えのように壊しやすいフェーズには**品質ゲート**（テスト全通過・件数を減らさない・既存の挙動の確認項目の一覧・確認方法）を付ける。
4. **md を先に書く**（正本）：`assets/plan-template.md` を土台に。節の構成は下の「構成」。
5. **HTML を書く**：`assets/plan-template.html` を土台に、**md と同じ内容**に図を足す。CSS はテンプレートのまま変えない。図は `references/svg-parts.md` の部品から。最低限：全体像（フェーズの箱と矢印）。あれば：共通化の「前／後」、状態遷移、処理の分かれ道（フロー）。
6. **図を確かめる**：ブラウザで開き、`references/svg-check.js` を実行して、箱からはみ出す文字が 0 件になるまで直す（文言を短くするか、箱を広げる）。ファイルを直したら、開き直してから確かめる（静的なスナップショットは再読み込みで変わらないことがある）。ブラウザが使えなければ、文字数 × 文字幅で見積もって確かめる。
7. **つなぐ**：仕様の文書の該当フェーズに、Issue 番号と計画への参照を書く。設計の資料に未決事項の節があれば「決めたこと（確定）」に直す。
8. **報告**：ファイルのパス、計画の要点（フェーズごとに 1 行）、コードを読んで見つけた「迷いやすい所」の上位 2〜3 件、次の段取り（別セッションのレビュー）と、`references/review-request.md` を埋めた依頼文。中身の全文はチャットに再掲しない。プロジェクトに報告の決まりがあれば従う（無ければ：作った・変えたファイル、コードを変えたか、できなかった確認）。

## 構成（md・HTML 共通。節番号も同じにする）
- 冒頭：**連動ルール**（下）、仕様の正（文書と章）、設計の資料、進め方・コミットの決まり（Issue を使うなら `Refs #N` / `Fixes #N`）
1. **全体像**：フェーズの流れ（HTML は SVG、md は 1 行の図）と各フェーズのコミット数、前提（新しい依存の有無・守る制約）、いまのテスト件数、品質ゲート
2〜5. **フェーズごと**：表（# ／ コミット ／ 内容 ／ テスト or 確認）＋完了条件。共通化のフェーズには「前／後」の図と「変えないこと」の注意
6. **ファイル構成**：`<pre>` のツリー。各行に「コミット番号 新規／変更：何を」
7. **実装の決めごと**：7.1, 7.2 … 迷いやすい所ごと。状態の表・図、分かれ道の図、具体的な API・値・文言
8. **リスクと対策**：表
9. **決定事項**：設計で決めたこと（質問と回答）。**「計画で決めたこと（仕様にない細部）」も分けて書く**（利用者が後で違うと言えるように）
10. **実装するセッションへの注意**：始める前（必要なファイルが見えるか・計画と仕様の食い違い・プロジェクトの決まり）、各フェーズの終わり（確認・進捗の更新・報告・止まる）、レビューを挟む所
- 末尾：**状態**（レビュー待ち／確定（レビュー反映済み））

フェーズの数・中身は機能に合わせて増減する（共通化が要らなければ消す、利用側が複数なら分ける）。要らない節・図は消す。

## 連動ルール（md と HTML の両方の冒頭に必ず書く）
> **連動ルール**：この md と `<名前>-plan.html`（図解）は対。**どちらかを直したら、もう一方も同じ内容に直す。**

- 計画を直すとき（レビューの指摘・実装中の変更）は、**必ず両方を手で同じ内容に直す**。片方だけ直して終わらない。
- 表・箇条書きの文言は両方で同じにする（HTML の図のラベルだけは短くしてよい）。
- 仕様の文書と食い違ったら仕様が正。計画を直す。

## 守ること
- 出力先：設計文書のフォルダ（`docs/` など）があればそこ、無ければ作業ディレクトリ直下。ファイル名は `<課題番号か機能名>-plan.md` と `<同じ名前>-plan.html`。同じ機能の設計・レビューの資料があれば名前をそろえる。
- 事実と推測を分ける。コードで確かめたことだけ断定し、実物で確かめられていないことは「要確認」「推測で設計」と書き、確かめるフェーズを書く。
- コミット・push・Issue の操作は、頼まれたときだけ（このスキルは文書を作るだけ）。
- プロジェクトの決まりの禁止事項に反する計画を書かない。機密（認証情報・個人情報・ログの本文など）を引用しない。
- 言語はユーザーに合わせる（テンプレートは日本語。英語で頼まれたら見出しも英語に）。
