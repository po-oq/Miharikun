Issue #16：導入前のセッションがタイムラインで更新されない（レビュー）

Issue の問い：「cursor で hook を入れる前のセッションを表示していて、hook 入れたあとにそのセッションをタイムラインで見ても更新されない。アプリ再起動すると更新される。この挙動は意図したものか」

1. 結論

直してから進める（仕様どおりの動きだが、使い方に合っていない。要件の見直しとあわせて直す）。

  • 意図したものか：半分は意図どおり。導入前の過去セッションは「起動後の最初の 1 回だけ transcript から取り込む」と要件・実装・テストの 3 か所で決めている。その結果、取り込み済みのセッションは、transcript が増えても画面が変わらず、再起動で取り込み直されたときだけ増える。
  • ただし「導入前のセッションを、導入後も続けて使う」ことは普通にある使い方で、画面が止まるのは仕様の抜け。直すほうがよい。
  • 要確認：Cursor で続けた会話に、hook のイベントが実際に届いているか。届いていれば画面は更新されるはずなので（Core のテストで確認済み）、Issue の症状は「hook が届いていない会話」で起きていると読める。ボスの環境で下の「確かめ方」を試してほしい。

2. 確認した範囲

3. 概念図

いま：取り込みは 1 回だけ。続きは hook が届いたときだけ画面に出る

修正後：取り込み済みの transcript の変化も、3 秒の巡回で拾う

4. 問題一覧

#重大度何が問題か（根拠）どう解決するか
1高 導入前のセッションは、起動後に 1 回だけ取り込み、その後は読み直さない（CursorSessionSource.cs:185 の _importScanned と :199、要件 11章「起動後の最初の Refresh で 1 回だけ」）。取り込み済みで hook が届かない会話は、transcript が増えても画面が変わらない。再起動すると Scan が走り直すので増えて見える。これが Issue の症状。 取り込み済みのセッションごとに、transcript のサイズと更新日時を覚える。巡回（3 秒）のたびに見て、変わったものだけ ReadEvents して Replace を出す。hook のファイルが出来たものは今までどおり捨てる。
・CursorTranscriptImporter：Scan とは別に、Rescan(known)（変わった分だけ返す）を足す
・CursorSessionSource.ImportTranscripts：「最初の 1 回」を「毎回、変わった分を確認」に変える
・要件 11章の「1 回だけ」を書き換える／テスト A_transcript_is_imported_once_and_not_reported_again は「変わらなければ報告しない」に直す
2中 hook のイベントが届いた時点で、取り込み分は丸ごと捨てて hook のイベントだけにする（CursorSessionSource.cs:63-76）。hook は導入後の分しか持たないので、導入前の履歴がタイムラインから消える。要件 11章も「hook のイベントに切り替える」と書いていて、これも仕様どおりだが、Issue の「更新されない」と合わせて混乱を招く。 案は「決めたいこと Q1」。
3要確認 hook が届かない会話が実際にあるのかは、コードからは言えない。この PC の events\cursor\ には 3 本あるが、どの会話か、続きが追記されているかは未確認（中身は読まない決まり）。 下の「確かめ方」で、ボスの環境で確認する。#1 の修正は、hook の有無にかかわらず入れてよい。
-問題なし 取り込み済み → hook への切り替えは、Remove と Append を同じ回に出すので、画面は 1 回の更新で置き換わる（ProjectEventStore.Apply、MainViewModel.Apply、テスト Hook_events_appearing_later_replace_the_imported_session）。TimelineViewModel.SetEvents も、先頭から違えば全部差し替える作りで、ここに止まる原因は見つからなかった。

確かめ方（要確認 #3）

  1. 導入前から続けている会話を Cursor で 1 回動かす。
  2. エクスプローラーで %LOCALAPPDATA%\Miharikun\events\cursor\ を開き、その会話の ID のファイルがあるか、更新日時が動いたかを見る（中身は開かない）。
  3. 無い／動かない → hook が届いていない（#1 の症状）。ある → 画面が止まる別の原因があるので、再現手順を教えてほしい。

5. 決めたいこと

Q1. hook が届き始めた会話で、導入前の履歴（transcript 由来）をどうするか。
A) 今のまま、hook のイベントだけにする … 実装は不要／履歴が消えて見え、混乱しやすい
B) 履歴（取り込み分）の後ろに hook のイベントをつなぐ … 続けて読める／取り込み分と hook 分の境目の扱い（二重に出ない保証、時刻なしと時刻ありの混在）が要る
推奨：今回は A のまま、#1 だけ直す。B は別 Issue にする（境目の仕様を決めてから）。履歴が消えることは、画面か要件に 1 行書いておく。
Q2. 取り込み済みの再確認の間隔。
A) 既存の 3 秒の巡回に乗せる … 実装が簡単／transcript の stat を 3 秒ごとにする（セッション数ぶん。軽い）
B) 取り込み先のフォルダも FileSystemWatcher で監視する … 反応が早い／監視先が増えて、作りが複雑になる
推奨：A（Cursor の hook 以外の更新は、すぐ見えなくてよい）。

6. リスクと対策

リスク対策
transcript が大きいと、変わるたびに全部読み直して重い変わったものだけ読む。会話中は書き込みが続くので、更新日時が 1 秒以内に変わった分は次の巡回に回す（間引き）。まず測って、遅ければ入れる
書き込み途中の行を読んで、壊れた行として落とす今の ReadEvents が行単位で壊れた行を飛ばすか確認し、飛ばせないなら末尾の不完全な行を無視する。要確認
タイムラインの「再取り込み」で、強調行・スクロール位置が飛ぶSetEvents は先頭からの共通部分を残して差し替える。取り込み分の時刻は取り込みの時点（更新日時）なので、毎回変わると全差し替えになる。イベントの時刻は前回の値を引き継ぐか、同じ内容の行は据え置く（要確認）
要件 11章の「1 回だけ」を変えるので、仕様と実装がずれる実装と同じ PR で要件 11章を書き換える（CLAUDE.md の「仕様の正」に従う）
