1. 結論

直してから使い続けたい問題が 2 件（どちらも「プロジェクトの中のファイル」をきっかけに、利用者が意図しないプログラムが動きうる）。ほかに低い問題が 2 件。 Hook・会話ログの読み取り・保存先のパス・git の引数・リリースの workflow は、問題なし。

前提とする脅威：Miharikun が見るプロジェクトのフォルダには、利用者が書いていないファイルが入りうる（clone した他人のリポジトリ、PR のブランチ、AI エージェントが書いた文書）。それらを「見るだけ」で何かが起動するのは避けたい。

1高 プレビューの中の移動で、プロジェクト内の任意のファイルが関連付けで起動される。
・md の生の HTML を止めていない（MarkdownRenderer.cs:19-22。Markdig の既定は HTML をそのまま出す）。html は設計どおり JS を実行する（要件 12.7）。

② ネットワークのパス（Uri.IsUnc、\\ で始まる）は、存在の確認もせずに捨てる。
③ md の一時 HTML に CSP を入れる：script-src を、Miharikun が入れるスクリプト（nonce）と CDN だけにする。md に書かれた <script>・onerror などは動かなくなる（Q2）。html は設計どおり JS を動かすので、①②が本命。
④ テスト：PreviewNavigationPolicy に「振り分け先」を返す関数を足し、拡張子・UNC・対象フォルダの外を表で試す。
2高
（Windows）		 git と explorer を名前だけで起動しているので、プロジェクトのフォルダにある同名の exe が先に選ばれうる。

・.NET は Windows でこの名前を自分で解決せず、OS の探す順（図の ①〜⑤）に任せる。② に親プロセスのカレントフォルダが入る。
・README の手順は「プロジェクトのフォルダで Miharikun.exe を起動」（README-win.txt の 2、App.axaml.cs:53-54）なので、カレントがプロジェクトになる。git status は起動直後に走る（AppComposition.cs:79）。

② explorer は Path.Combine(Environment.GetFolderPath(SpecialFolder.Windows), "explorer.exe") のフルパスで起動する。
③ テスト：GitLocatorTests に Windows の場合を足す（相対の PATH 項目は無視する、フルパスを返す）。ShellOpenTests の組み立ての期待値をフルパスにする。
④ Windows の実機で、カレントを試験用のフォルダにして起動し、git の実体がフルパスで選ばれることを確かめる（直す前の再現も、無害な exe を使って試験用のフォルダで行う）。
3低 プレビューが CDN のスクリプトを、版の固定と完全性の確認なしで読む。
mermaid は mermaid@11（11 系の最新に自動で変わる）、highlight.js は 11.9.0 固定。どちらも integrity 属性なし（MarkdownRenderer.cs:14-15・107-124）。CDN 側が書き換えられると、プレビューの中で任意のスクリプトが動く。#1 が残っていると、影響が大きくなる。md を開くたびに CDN へ通信が出る（どの時刻に文書を見たかが CDN に分かる）。 		A) mermaid と highlight.js を Miharikun.Docs に同梱し、一時 HTML の隣に置いて読む（オフラインでも図と色が出る）。
B) 同梱しないなら、版を完全に固定し（例 mermaid@11.x.y）、integrity と crossorigin を付ける。mermaid は ES module の import() なので、<script type="module" src integrity> に書き換える要あり（Q3）。
4低
（参考）		 README が Hook の置き場所の例に C:\dev を挙げている。
C ドライブの直下に作ったフォルダは、既定のアクセス権で、同じ PC のほかの利用者も中のファイルを書き換えられる。共用の PC だと、ほかの利用者が Hook exe を差し替え、Cursor 経由で自分の権限で動かされうる（scripts/dist/README-win.txt の「会社の PC などで…」）。1 人で使う PC なら影響はない。 		README の例を %USERPROFILE% の下（例 C:\Users\<名前>\tools）に変える。または、C 直下に作るなら、ほかの利用者の書き込みを外すよう一言添える。

#回答（2026-10-09）
Q1C：開いてよい種類（画像・PDF・テキスト・md/html）だけ既定のアプリで開き、ほかは起動せず Finder／エクスプローラーで見せる
Q2A：md の生の HTML は残し、CSP（nonce）でスクリプトだけ止める
Q3A：mermaid・highlight.js を同梱する（CDN をやめる）
追加診断の後の相談：Claude の会話ログの保険の探索（名前で見つからないとき、ほかのプロジェクトのログの先頭の cwd を読む）は残し、フォルダごとに cwd が取れた最初の 1 ファイルで打ち切って、読む量を減らす（Phase 46）

反映先：要件定義（13 章・12.7・12.10・8.2・9.1・7 章の処理 2、15 章の Phase 42〜47）、実装計画 docs/security/security-plan.md（図解 security-plan.html）。以下は回答前の選択肢（記録として残す）。

Q1.（#1）プレビューのリンクで、md/html 以外のローカルのファイルをどう扱うか
A) 起動しない。Finder／エクスプローラーで、そのファイルを選んだ状態で見せる … 利点：スクリプトからでも何も起動しない。欠点：PDF や画像へのリンクも 1 手間増える
B) パスを見せて「開きますか？」と確かめてから、関連付けで開く … 利点：今の使い方に近い。欠点：毎回の確認に慣れて、押してしまいやすい
C) 拡張子の許可リスト（pdf・png・jpg・txt など）だけ関連付けで開き、ほかは A … 利点：よく使う物は今のまま。欠点：リストの手入れが要る
推奨：C（画像・PDF のリンクは今のまま使え、実行形式は確実に止まる。迷ったら A から始めてもよい）
Q2.（#1）md の中の生の HTML をどうするか
A) HTML は残し、CSP（nonce）でスクリプトだけ止める … 利点：<details>・<br>・幅を指定した <img> など、今の md の見た目が変わらない。欠点：CSP の文字列を保つ手間
B) Markdig の DisableHtml() で、生の HTML を文字として出す … 利点：いちばん簡単で確実。欠点：HTML を使った md の見た目が変わる
推奨：A（GitHub で見たときと同じ見た目を保てる）
Q3.（#3）CDN のスクリプトをどうするか
A) 同梱する … 利点：オフラインでも動き、外への通信が無くなる。欠点：配布物が数 MB 増える
B) 版の固定と integrity … 利点：配布物が増えない。欠点：mermaid の読み込み方を変える要あり。オフラインでは今と同じく図にならない
推奨：A（#3 の問題とオフラインの不便が両方なくなる）
