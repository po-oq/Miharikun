3. 問題一覧

#重大度何が問題か（根拠）どう解決するか
1高③ 2 回目以降の走査中に来たリンクが消える。計画 7.3-2 は「最初の走査が終わったら RestoreLastOpened の代わりに予定を選ぶ」。しかし走査は最初の 1 回だけではない：Rescan() は索引を _index.Reset() で空にする（DocumentsViewModel.cs:219）、除外設定の保存（:235-239）・フォルダの変更やバッファあふれ（:65・:284-285）・「読み直し」で走る。このとき索引に無いので予定に入るが、Start() は何もせず（:203-205）、最後のバッチでは _restored が true なので何も選ばない（:266-270）。タブは切り替わるのにファイルが選ばれない。 予定は「最初の走査」でなく毎回の走査の終わり（batch.IsLast）で見る。あれば索引から選ぶ（無ければ既定のアプリ＋ログ）、その後 _restored=true。予定が無いときだけ、従来どおり !_restored で RestoreLastOpened。上の図の「修正後」。計画 7.3-2 の文言と、25-2 の確認に「読み直しの最中にメモのリンクを押す」を足す。
2高③ 走査済みなのに索引に無いと、予定が残り続けて何も起きない。計画は「無ければ（まだ走査していない・走査中）」と書くが、判定は索引の有無だけ。DocumentLinkRule は除外と拡張子だけ見るので、走査が終わった状態で索引に無いことがある（作った直後で Watcher の差分が 200ms のまとめ・UI への Post 前、判定の直後に消えた、など。:245・:273-287）。このとき Start() は何もしないので、予定は次の走査まで残り、無関係な時に急に選ばれる。 OpenFromOutside を 4 分岐にする：①索引にある→選ぶ ②!_started→予定＋Start() ③IsScanning→予定 ④それ以外→その場で既定のアプリで開き、ログ（計画の「走査が終わっても無ければ」と同じ扱い）。IsScanning は既にある（:190）。
3高④ 読み込み失敗を「空」と扱うと、保存で既存のメモを消す。23-1 の Load は「無い→空・null」だけ決めていて、ファイルはあるが読めない（ロック・権限・AtomicFile の置き換えの瞬間など）ときが未定。VM が空として表示すると、利用者は「メモはまだありません」→「編集」→保存で、元のメモを空や新しい文で上書きする（AtomicFile.WriteAllText は無条件に置き換える：AtomicFile.cs:27-30）。7.6 の監視での読み直しも同じで、一時的な失敗で空のプレビューになる。 Load は「ファイルが無い」だけを空にし、それ以外の IOException・UnauthorizedAccessException は例外のまま呼び手へ（Save と同じ方針）。VM：最初の読み込みで失敗→バーに理由、「編集」を押せなくする（メッセージで案内）、タブを開き直すか外の変更で再試行。監視での読み直しの失敗→今の表示のまま（ログだけ。OnExternalChange を呼ばない）。23-1 のテストに「読めないとき例外」を足す。
4中④ MemoEditor の名前がぶつかる。23-2 にプロパティ Saved とメソッド Saved(text) が並んでいる。C# では同じクラスに同名のプロパティとメソッドは置けない（CS0102）。 メソッドを MarkSaved(text)（または OnSaved）に。7.1 の表も同じ名前に揃える。
5中④ 編集中に外で変わったあと「キャンセル」すると、プレビューが古いまま。7.1：編集中の外の変更は Saved だけ変える（正しい）。7.6：「作り直すと返ったときだけ PreviewChanged」。Discard() は「表示は Saved」とあるが、作り直しを出すか決まっていない。プレビューの WebView2 は編集の前の内容を持ったまま（DocumentPreview.xaml.cs:98-104 は来たときしか描かない）。 Discard()（と保存なしで戻る場合）は「作り直すか」を返す：編集の始めに表示していた内容（EditBase）と今の Saved が違えば true。VM は true のとき PreviewChanged(Markdown, reload:true)。テストに「編集中に外で変更→破棄→作り直す」を足す（23-2 のテスト欄の「破棄後は新しい内容」をこの形で確かめる）。
6中④ 変更していないのに「保存」を押すと、外の更新を古い内容で戻す。編集中に別の起動が書き換え → こちらは何も変えずに保存 → Draft（＝編集の始めの内容）を書くので、相手の変更が黙って消える。「後勝ち」は両方が変えたときの話で、こちらが何も変えていないのに消えるのは利用者の予想と違う。 保存の時 !IsDirty なら書かずにプレビューへ戻る（#5 と同じく、Saved が変わっていれば作り直す）。7.1 の表に 1 行足す。
7中① 共通部品に、ドキュメント用の文言が埋まったまま。XAML の既定文「ファイルを選ぶと、ここに表示します」（DocumentPreview.xaml:10）、null のときの同じ文（.xaml.cs:66）、Runtime 未導入の案内「ツリー・一覧・概要は使えます」（:137-138）。メモタブでは、読み込み前の一瞬と Runtime 未導入のときに、間違った案内が出る（12.10 は「編集・保存は使える」）。 文言をホストから渡す：IPreviewHost に EmptyText（null の時の文）と RuntimeMissingNote（2 行目）を足す。ドキュメント VM は今の文をそのまま返す（挙動不変）。XAML の既定文は空にし、DataContext が付いた時に EmptyText を入れる。または「null を出さず Message を出す」に統一してもよいが、ドキュメント側の差分が増えるので前者を推奨。
8中② 環境の共用で、失敗したときにやり直せなくなる恐れ。今は失敗時に _initTask = null にして次の選択でやり直す（DocumentPreview.xaml.cs:162-169）。WebViewEnvironment.GetAsync が「最初の 1 回の Task」をそのまま覚えると、失敗した Task を返し続け、両方のタブで二度と始まらない。 GetAsync は、覚えた Task が失敗・キャンセルなら捨てて作り直す（成功した環境だけ覚える）。Runtime の有無の確認（GetAvailableBrowserVersionString）は結果を返すだけにし、案内の文はそれぞれの部品が #7 の文言で出す。UI スレッドから呼ぶ前提をコメントに。
9中③ 「選ぶ → タブ切り替え」の順だと、隠れたタブでプレビューが動く。計画 7.3-1 は OpenFromOutside を呼んでから切り替えを頼む。索引にあれば SelectPath がすぐ RaisePreview（DocumentsViewModel.cs:156）し、ドキュメントタブが一度も表示されていなければ WebView2 を隠れた場所で作り始める。今のコードは「画面に載った（ウィンドウハンドルのある）コントロールが要る」前提（DocumentPreview.xaml.cs:149-155）。WPF の WebView2 がハンドルを待ってくれるかは要確認。 順番を逆にする：MainWindow がタブを切り替え → Dispatcher.BeginInvoke(DispatcherPriority.Loaded, …) で OpenFromOutside。こうすると DocumentsView.Loaded の Start()（DocumentsView.xaml.cs:12）が先に走り、今の「タブを開いてから選ぶ」と同じ道を通る。計画 7.3-1・7.3-4 の文言を直す。
10中⑤ ボタンの名前が要件と合わない。要件 12.10 と設計イメージは［保存］［保存しない］［キャンセル］。計画 7.4・7.5 は既存と同じ MessageBox（HookSetup.cs:62-67）で「はい＝保存／いいえ＝保存しない」。標準の MessageBox はボタンの文字を変えられない。 下の Q1。どちらかに決めて、要件か計画の片方を直す。
11低③ 最初の走査中に索引にあって選んだあと、RestoreLastOpened がもう一度選ぶ。（図の B）SelectPath は lastOpened を保存するので普通は同じファイルになり、プレビューを 2 回出すだけ。ただし設定の保存に失敗したとき（ProjectSettingsStore.cs:65-72 はログだけ）は前回のファイルに戻る。 #1 の修正で、OpenFromOutside が選んだら _restored = true にする。
12低③ 予定がある間に利用者が自分で選ぶと、走査の終わりで予定に上書きされる。 OnSelectedRowChanged（:410-419）で予定を消す。
13低③ 「パスで絞り込み」が入っていると、一覧に出ない。SelectPath は絞り込みを変えない（:145-157・:312）。プレビューには出るが一覧で選ばれない。ドキュメント内のリンクも今同じ動きなので、挙動としては揃っている。 今のままでよい（揃っている）。気になるなら OpenFromOutside だけ絞り込みを空にする。計画に「今と同じ」と一言書いておく。
14低③ 除外の判定を二重に作らない。23-3 の DocumentLinkRule のテストに「親の除外も」とあるが、既に GitIgnoreMatcher.IsPathExcluded（GitIgnoreMatcher.cs:35-42）が親までさかのぼる（Watcher も同じものを使う：DocumentChangeClassifier.cs:54）。また今の「対象フォルダ内か」は rel.StartsWith("..")（DocumentsViewModel.cs:135）で、..memo.md のような名前を外と誤判定する。 DocumentLinkRule は IsPathExcluded(rel, false) と DocumentEntry.TryGetKind を呼ぶだけにする。内外の判定は「最初の区切りまでが ..」で見る（新しいコードだけ。既存の OpenLocalLink は Phase 24 では変えない）。
15低① PreviewSource.File(FullPath, Kind) に相対パスが無い。今は失敗のログに target.RelativePath を使う（DocumentPreview.xaml.cs:88）。無くすとログの文が変わる（挙動不変の範囲が少しずれる）。 File(FullPath, RelativePath, Kind) にする（今の PreviewTarget と同じ項目）。メモの Markdown はログに Title を使う。
16低④ 保存のあと「最終更新」の日時をどこから取るか未定。23-1 の Save は戻り値なし、MemoEditor.Saved(text) も日時を持たない。要件 12.10 は「メモのファイルの更新日時」。外の変更のときも同じ。 Save が書いた後の LastWriteTime を返す（または VM が File.GetLastWriteTime）。外の変更の読み直しも Load の日時でバーを更新。25-1 の確認に「保存で日時が変わる」を足す。
17低⑤ Windows のサインアウト・シャットダウンでは Closing が来ない（WPF は Application.SessionEnding を出し、Window.Closing は出さない仕様。要確認）。未保存の入力は黙って消える。要件には書かれていない。 下の Q2。最小なら「既知の制限」として計画に書く。
18低⑤ MemoViewModel の後始末が計画に無い。App.OnExit は今 _viewModel・_documents・_monitor だけ Dispose（App.xaml.cs:74-79）。メモの FileSystemWatcher（7.6）とまとめ用のタイマーが残る。 25-1 の App.xaml.cs の変更に「OnExit で Dispose」を足す。theme.Changed の購読も MainWindow（MainWindow.xaml.cs:28）と同じ所に足すと書いておく。

4. 決めたこと（2026-10-04：Q1＝B、Q2＝A で確定）

Q1 → B：閉じるときの確認は専用ダイアログ［保存］［保存しない］［キャンセル］。要件 12.10 はそのまま（すでにこの文言）。計画 7.4・7.5 の「既存と同じ MessageBox」を直し、6 章のファイル構成に専用ダイアログ（例 Views/UnsavedMemoDialog.xaml(.cs)、25-2）を足す。キャンセルの確認（「変更を破棄しますか？」）は MessageBox のまま。
Q2 → A：サインアウト・シャットダウン時の未保存の入力は扱わない。計画 7.5 に「既知の制限」として明記する。
Q1. 閉じるときの確認のボタン（#10）
A) 標準の MessageBox（はい／いいえ／キャンセル）にして、本文に「はい＝保存、いいえ＝保存しない」を書く。要件 12.10 の文言を直す … 利点：既存の確認と見た目が揃い、コードが小さい／欠点：ボタンの文字が要件と違う
B) 小さな専用ダイアログ（［保存］［保存しない］［キャンセル］）を作る … 利点：要件どおり、押し間違いが減る／欠点：ダイアログ 1 つ分（xaml・テーマ対応）増える。キャンセルの確認（「変更を破棄しますか？」）は はい／いいえ で困らない
推奨：B（入力を失うかどうかの確認で、ボタンの意味を本文で読み替えさせるのは間違いやすい。既に AppSettingsDialog などの専用ダイアログがあり、作り方は揃えられる）。A なら要件 12.10 を先に直す。
Q2. サインアウト・シャットダウンで未保存の入力（#17）
A) 何もしない。計画に「既知の制限」と書く … 利点：作業なし／欠点：まれに入力を失う
B) App.SessionEnding で、変更があれば止めて確認する（e.Cancel）… 利点：失わない／欠点：Windows の終了を止める動きになり、要件に無い
推奨：A（要件に無く、頻度も低い。まずは制限として明記し、困ったら相談）。
