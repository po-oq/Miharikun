A1. ReadNew の途中の例外で、差分を取りこぼす

何が起きるか

CursorSessionSource.ReadNew（CursorSessionSource.cs:51-99）は、ファイルを 1 本ずつ読んで deltas に積み、最後にまとめて返す。ファイルごとの catch は IOException だけ（88 行）。それ以外の例外は ReadNew の外へ抜け、Store の catch (Exception)（ProjectEventStore.cs:303）で止まる。このとき、積んであった差分は全部捨てられる。一方で、読み終えたファイルの読み取り位置（JsonlTail の offset）は進んだまま。そのため、次の回にも同じ行は読まれず、アプリを再起動するまでそのイベントは画面に出ない。

a.jsonl を読む
offset 進む・差分を積む→ b.jsonl を読む
offset 進む・差分を積む→ c.jsonl を開く
UnauthorizedAccessException→ ReadNew の外へ抜ける
a・b の差分は捨てられる→ 次の回：a・b は offset が進んでいるので
同じ行はもう読まれない ＝ 取りこぼし

実際に起こりうる例外

  • UnauthorizedAccessException：IOException の仲間ではない。アクセス権の問題で new FileStream（JsonlTail.cs:26）が投げる。共有違反は IOException だが、アクセス拒否はこちら。
  • 取り込みの Scan の例外：ImportTranscripts（178-191 行）は、Scan を呼ぶ前に _importScanned = true にしている（182 行）。Scan が投げると、その回の Hook の差分が全部捨てられる。しかも 次の回からは取り込みを試しもしない（導入前のセッションがこの起動の間ずっと出ない）。
  • Normalize は TryGetValue で守っているので投げにくい。ただし将来のバグや OutOfMemoryException（巨大な追記）は否定できない。

旧コードでは、これらはプロセスごと落ちていた。だから悪化ではない。ただ、「Store の catch で他の Source を続ける」（A6）を入れたことで、落ちずに静かに欠けるという新しい状態ができた。それを防ぐのは Source の役目になる。

どう直すか

方針：Source の中でファイル単位・取り込み単位に例外を閉じ込め、それまでに積んだ差分は必ず返す。Store の catch は「最後の砦」のままにする。

catch (Exception ex)   // UnauthorizedAccessException など。ほかのファイルの差分は返す
{
    _log?.Invoke($"{path} の読み込みに失敗: {ex}");   // スタックつき
}

補足：ファイル 1 本の中で、offset が進んだあとに例外が出たとき（Normalize の途中など）のその回の行は、上の修正でも失われる。完全に防ぐには、JsonlTail に「読んだが確定していない」状態を持たせ、成功してから offset を確定する必要がある。そこまでは不要と考える（いまの Normalize は投げにくい）。代わりに、ログにスタックが残ることを優先する。

テスト（Cursor の Source 側に足す）：

  • 「Scan が投げても、同じ回の Hook の差分は届く。次の回に取り込みがもう一度走る」。Scan を投げさせる方法は、Importer の中を見て決める（読めないフォルダを置く、など）。

B1. 取り込み済み → Hook の切り替え：Remove を先に出すのは正しい。後ろの Replace が要らない

Remove を先に出すこと（依頼文の問い）への答え：妥当。むしろ必要

Source の中の辞書（_files・_imported）は大文字小文字を区別しない。一方、Store のキー SessionKey は区別する。ID が大文字小文字だけ違うと、計画どおり「Hook の Replace だけ」を出した場合、取り込み分が別のキーとして Store に残り、同じセッションが 2 枚になる。

Store: cursor/ABC（取り込み分）＋ Hook ファイル abc.jsonl が現れる →
出す差分Store の結果
計画どおり：Replace(cursor/abc, Hook) だけcursor/ABC（取り込み）と cursor/abc（Hook）の 2 つNG（旧と違う）
実装：Remove(cursor/ABC) → Replace(cursor/abc, Hook)cursor/abc だけ旧と同じ

大文字小文字が同じときも、Remove(K) → Replace(K) は同じキーへの順の適用で、結果は同じ。Refresh の戻り値も重複を除いているので、通知は 1 回になる。旧（git show d3b7178 の ImportTranscripts 80-89 行）も「Hook のファイルがあれば、プロジェクトが一致するかどうかに関係なく取り込み分を消す」なので、Remove を無条件に出すのは旧と同じ動き。8.1 の 6 行目（別プロジェクトなら Remove）も、これで満たしている。

問題：そのあとの Replace は要らず、罠になる

ReadFile の 173 行は、切り替え中のファイルの差分を Replace にしている。しかし events は今回読んだ分だけ。Replace は「保持しているもの全部をこれに置き換える」という意味なので、もしそのファイルのイベントがすでに Store にあれば、前の分が消える。

前の回：abc.jsonl の E1 を Append 済み→ 今回：switching に abc→ Replace(abc, [E2])
→ E1 が消える

いまは、この状況はほぼ起きない。取り込みの Scan に渡す File.Exists は Windows では大文字小文字を区別しないので、すでにある Hook ファイルの ID は取り込まれない。だから、切り替えになるのは「新しく現れたファイル」だけで、events は先頭からの全部になる。ただ、これは Importer の判定に寄りかかった偶然で、Replace の意味（全部を渡す）とずれている。Claude の Source を書くときに同じ形を真似すると、そのまま事故になる。

どう直すか

先に Remove を出しているので、Hook の差分はふつうの差分でよい。Remove のあとの Append は、空の Store に足すだけなので、結果は Replace と同じ。

B2. 消えて作り直されたフォルダの Watcher が残る

SessionMonitor.EnsureWatchers（SessionMonitor.cs:49-93）は「フォルダが無ければ Watcher を捨てる」。しかし、3 秒の間に消えて同じ名前で作り直された場合、Directory.Exists は true なので、古いフォルダを見ていた（もう通知の来ない）Watcher が残り、張り直されない。

Watcher(dir) 動作中→ dir 削除（Watcher は Error を出して止まる）→ dir 作り直し→ 次のポーリング：Exists=true なので張り直さない→ 以後は 3 秒ポーリングだけ（300ms → 最大 3 秒の遅れ）

Cursor の events ではまず起きない。ただ、Phase 20 の Claude では、作業ツリーのフォルダ（worktree を消して同じ名前で作り直す）で起こりうる。取りこぼしではなく遅れるだけなので、軽い。

どう直すか

Error を受けたら、その Watcher に「作り直す」印を付ける。次の EnsureWatchers で、印の付いた Watcher を捨てて張り直す。

private readonly HashSet<(string, string)> _broken = [];   // _gate で守る
...
w.Error += (_, _) => { lock (_gate) _broken.Add(key); Schedule(); };
...
// EnsureWatchers の先頭
foreach (var (key, watcher) in _watchers.ToList())
{
    if (_broken.Remove(key) || !Directory.Exists(key.Directory))
    {
        watcher.Dispose();
        _watchers.Remove(key);
    }
}

注意：Error の中で lock (_gate) を取るので、Dispose（ロックの中で watcher.Dispose()）と待ち合いにならないか確かめること。FileSystemWatcher.Dispose がハンドラーの終わりを待つことはないので、デッドロックにはならないはず。ただし、Error はバッファあふれでも来るので、そのたびに張り直すことになる（実害はない）。

ロックの中の重さ（依頼文の懸念）：3 秒ごとに Directory.Exists を「Watcher の数＋監視先の数」回呼ぶだけ。_store.Refresh()（ファイルの読み込み）自体が同じロックの中なので、そちらのほうがずっと重い。今のままでよい。ネットワークドライブの対応は、このツールの範囲外。

Dispose と RefreshNow の競合：問題なし。_disposed をロックの中で立て、RefreshNow もロックの中で見ている。タイマーの破棄はロックの外だが、その後にコールバックが来ても、_disposed を見て何もしない。取り直しで Watcher が増え続けないか：(Directory, Filter) をキーにした辞書で重複を防いでいるので、増え続けない。
