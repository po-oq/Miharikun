2. A：このままだと困る（計画の変更が必要）

A1. Claude のセッションに「コミット」が出ない （重大）

問題：詳細のコミット一覧は、Hook が記録した HEAD の範囲で git log している。

MainViewModel.LoadCommits(s)  →  _git.GetCommits(s.StartHead, s.LatestHead)
GitClient.GetCommits:  if (fromHead is null || toHead is null ...) return null;   // GitClient.cs:70-73 → 画面は「—」

Claude の会話ログには gitBranch しか無く、HEAD（hash）が無い（要件 5.1 の表にも「hash は無し」）。なので、Claude のセッションは常にコミット「—」。要件 5.1 には「コミット判定は App が git で行う」とあるが、その方法が計画のどこにも無い。Phase 22-1 の目的「成果（コミット・テスト実行）の見え方を確認」が果たせない。

解決（実ログで確かめた結果、案を変えた）：ログにある「ブランチ（gitBranch）と時刻」から、App が git で開始・最新の HEAD を求める。求めた HEAD を既存の GetCommits にそのまま渡せるので、画面とコミット一覧の処理は変えずに済む。

 Claude の要約：StartedAt（最初の timestamp）, LastActivityAt, Branch（gitBranch）
        │
        ▼  GitClient に 1 つ足す（Core。テストは一時リポジトリで。GitClientTests と同じ流儀）
 StartHead  = git rev-list -1 --before=<StartedAt>      <branch>   … 開始の直前のコミット
 LatestHead = git rev-list -1 --before=<LastActivityAt> <branch>   … 最後の動きの時点のコミット
        │
        ▼
 既存の GetCommits(StartHead, LatestHead)  →  git log StartHead..LatestHead（Cursor と同じ）
  • 最初の案（git commit の出力から SHA を拾う）は捨てた。実ログでは、git commit を含むコマンド 105 件のうち、出力に [main 1a2b3c4] … の行があったのは 30 件だけだった。-q を付けたもの、git log --oneline -1 や push の出力だけが残るもの、などがあるため。
  • reflog（HEAD@{時刻}）を使う案も捨てた。このリポジトリの reflog は 10/3 からしか残っていない（clone し直したため）。それより古い時刻を指定すると、警告を出して一番古い記録を返すので、古いセッションで誤る。rev-list --before はコミットの日時で探すので、reflog に頼らない。
  • 同じブランチで並行して動いた別のセッションのコミットも混ざる。ただし、Cursor の今の方式（開始 HEAD..最新 HEAD）も同じなので、挙動はそろう。
  • ブランチ名は、オプションとして解釈されないよう検証する（先頭が - なら使わない。git check-ref-format --branch で確かめる）。HEAD（detached）や、取れないときは null で、画面は「—」（今と同じ）。
  • 作業ツリーのセッションも、ブランチは本体のリポジトリから見えるので、同じ方法で求められる。
  • 時刻は、ターンの途中を含めないように「最後の動き」を使う。git の呼び出しは選択中のセッションだけで、範囲が変わったときだけ（今の _commitRange の仕組み）。
  • 計画：19-5 ブランチと時刻からの HEAD（GitClient。テスト先行）を追加し、21-3 の LoadCommits で、HEAD が無いセッションに使う。

  • 1 回の ReadNew で同じキーに複数の差分が来てよい（順に適用）。Refresh が返す「変わったキー」は重複を除く（旧 86 行の !changed.Contains と同じ）。
  • 「照合前に捨てた行の読み直し」（DroppedLines）は Source の中で完結し、Store には最初の一致時に Append（空から）で出す。

A3. 裏で動かす（run_in_background）の Agent と Bash を誤判定する

問題：Claude Code は、サブエージェントやコマンドを裏で動かせる（このプロジェクトの作業でも使う）。この場合、tool_result はすぐ返る（「起動しました」の内容）。対応表どおりに変換すると：

 Agent(run_in_background)  tool_use ──▶ SubagentStarted
                           tool_result（すぐ。agentId つき）──▶ SubagentStopped   ← まだ動いているのに「動いていた」
                                                                     → 完了チェック「✓ 裏の作業なし」が嘘になる
 Bash(run_in_background)   tool_result（すぐ。"…running in background…"）
                           is_error=false ──▶ ToolSucceeded, ExitCode=0        ← dotnet test なら「テスト成功」と出る（嘘）

実ログで確かめた結果：

  • Bash は実際に起きている（1 件）。結果は is_error=false で、内容は「Command running in background with ID: …」。toolUseResult に backgroundTaskId がある。→ このまま変換すると「ExitCode 0 ＝ 成功」になる。
  • Agent は 84 件すべて同期。結果の toolUseResult.status は全部 completed で、run_in_background の指定は 0 件。status の欄があるので、completed 以外なら「まだ動いている」と判定できる。
  • 裏の作業の終わりは、origin.kind = "task-notification" の user 行（27 件）で届く。中身はタグつき（<tool-use-id>・<status> completed／failed・<summary>）。今回の 27 件は、すべて SendMessage のもの。人の入力ではないので、PromptSubmitted にしない（B11）。

解決：

  • Bash：input.run_in_background == true か、結果に backgroundTaskId があれば、ToolSucceeded にするが ExitCode = null（不明）。テスト実行は「結果不明」で出す（成功にしない）。
  • Agent：結果の toolUseResult.status が completed のときだけ SubagentStopped を出す。それ以外は「動いている」のまま。task-notification の <tool-use-id> が、その Agent の id と一致したら SubagentStopped を出す。実例が無いので、テストは手書きで作り、Phase 22 で実物が出たら確かめる。
  • 計画 19-1 / 19-3 のテストに「裏で動かす Bash」「status が completed でない Agent」「task-notification」を足す。

A4. 「停止」（StalledRule）の誤判定と、画面の食い違い

問題 1（誤判定）：本体のログに 10 分以上なにも書かれないが、止まっていない場面がある。

 ・サブエージェント実行中   … 中身は subagents\agent-<id>.jsonl に書かれ、本体は Agent の結果まで無音（数十分あり得る）
 ・長いコマンド             … dotnet test / publish.ps1 の結果待ち
 ・承認待ち（許可の確認）   … ログに記録が無い（14.2）。ボスの番なのに「停止」と出る

問題 2（食い違い）：計画 21-3 は「Tick で丸と文字だけ停止にする」。しかし画面の他の所は card.State を見ている。

 MainViewModel.Visible:   if (RunningOnly && c.State != SessionState.Running)   ← 「実行中のみ」に停止のカードが残る
 MainViewModel.UpdateCounts: Count(SessionState.Running) ...                    ← 件数「実行中 N」に停止が入る
 SessionDetailViewModel:  s.TurnInProgress ? "✗ ターン実行中"                    ← 詳細は実行中のまま
 SessionCardViewModel:    s.State == Running ? "💬 （応答待ち）"

解決：

  • Core に StalledRule.DisplayState(summary, now, timeout) を置き、表示用の状態を 1 か所で決める。カードに DisplayState を持たせ、丸・文字・絞り込み・件数・詳細ヘッダーは全部これを見る。Tick で変わったカードがあれば CardsView.Refresh() と UpdateCounts()。
  • 動いているサブエージェントか、結果待ちのツール（RunningTools）があるときは、停止にしない（または、しきい値を長くする）。表示は「🔵 実行中（N 分動きなし）」。
  • 結果待ちのツールが無く、動きなしのときだけ「🟡 停止（N 分動きなし）」。文字に「動きなし」を添えて、ボスが押した停止と区別する（承認待ちの可能性があるため）。
  • StalledRule のテストに「サブエージェント実行中」「ツール結果待ち」の 2 ケースを足す。

A5. テーマを切り替えると runningTimeoutMinutes が消える

問題：AppSettingsStore.SaveTheme は {"theme": …} だけの新しい JSON でファイルを丸ごと上書きしている（AppSettings.cs:45-47）。手で書いた runningTimeoutMinutes が、テーマの切り替えで消える。設定画面を作らない（ファイルを手で書く）方針なので、気づきにくい。

解決：保存は「読む → そのキーだけ変える → 書く」（知らないキーも残す）。19-4 に含め、テスト「テーマを保存しても他のキーが残る」を足す。

決定（利用者）：⚙ メニューに「設定…」を足し、アプリ全体の設定画面を作る。今は「停止とみなす時間（分）」だけで、今後の設定もこの画面に足す。保存するとすぐ効く。テーマは ⚙ メニューに残す。

 ⚙ ─┬─ Hook を導入 / 削除
    ├─ テーマ ▸ OS / ライト / ダーク ──┐
    ├─ ドキュメントの設定…（プロジェクトごと）│ どちらも settings.json に書く
    └─ 設定…（新。アプリ全体）─────────┘ → 「全体を読む → キーを変える → 全体を書く」で、互いに消さない

反映先：要件 6 章（settings.json）・12.9（新）・Phase 19 / 21・17 章（保留から外す）。計画 19-4（保存の直し）・21-4（新。設定画面）。

A6. Source の例外で、アプリごと落ちる

問題：SessionMonitor は System.Threading.Timer のコールバックで Refresh する。ここで処理されない例外が出ると、プロセスが終了する。旧 Store が捕まえているのは IOException だけ。Claude のログは形式が非公開で変わり得る。たとえば node["x"].GetValue<string>() は、値が文字列でないと InvalidOperationException を投げる（CursorTranscriptImporter がこの書き方をしている）。

解決：

  • Store：Source ごとに ReadNew を try/catch (Exception) ＋ログ。Claude 側が壊れても Cursor の表示は続く。
  • Normalizer：1 行ごとに try/catch（その行を「壊れた行」として飛ばす）。値の取り出しは TryGetValue だけを使う。
  • テスト：「型の違う値（数値の content など）でも止まらない」「片方の Source が投げても、もう片方の差分は届く」。

あわせて（利用者の質問「形式が変わったとき、ログに例外を出す設計か」への答え）：いまは出ない。知らない種類の記録は黙って飛ばし、欄の型が変わると落ち、捕まえていない例外の受け皿も無い（src を検索して 0 件）。次を足す：

  • 読めない行：ファイル名・行番号・種類・version・例外の種類とメッセージを app.log に。同じ種類のエラーは 1 ファイル 1 回＋最後に件数。行の中身は書かない（会話の本文が入るため）。
  • 知らない種類の記録・初めて見る version：起動ごとに 1 回、件数つき（形式が変わったことに気づくため）。
  • 捕まえられなかった例外（UI スレッド・背景スレッド・Task）：ex.ToString() を app.log に（18-5）。

決定（利用者）：画面に印は出さず、ログだけ。

反映先：要件 11.1・13 章・Phase 18 / 19。計画 18-2（Source ごとの隔離）・18-5（受け皿）・19-1（行ごとの例外とログ）。

A7. 監視先（WatchPaths）は固定ではない ＋ .claude にフォルダを作ってはいけない

問題：

  • 今の SessionMonitor.StartWatcher は Directory.CreateDirectory(_eventsDir) する。同じ処理を Claude の監視先にかけると、.claude\projects\ にフォルダを作る（読み取りだけの約束に反する）。
  • Claude の監視先はあとから増える。このプロジェクトで初めて Claude を使った時点や、作業ツリーを作った時点で、…--claude-worktrees-<名前> ができる。起動時に一度だけ WatchPaths を読むと、監視されない（3 秒のポーリングで拾えるが、Watcher は張られない）。

解決：

  • 監視先を作るかどうかは Source が決める。Cursor の events は従来どおり作る（挙動不変）。Cursor の Source の初期化で作るか、WatchPath(Path, CreateIfMissing) にする。Claude は作らない。
  • Monitor は、ポーリングのたびに Store から WatchPaths を取り直し、増えた分だけ Watcher を張る（無いフォルダは張らずに、次回また試す）。
  • Claude の Watcher は IncludeSubdirectories = false（subagents\ の頻繁な書き込みで、毎回読み直さないため）。

4. C：品質ゲート（Phase 18 を守る条件）の補強

今の 4 点（全テスト・AOT 警告 0・publish.ps1・隔離環境の目視）は必要だが、「既存テストが通る」は「既存テストが見ている所が変わらない」しか保証しない。旧 Store には、テストの無い経路がある。

C1. 移す前に「特性テスト」を足す（新コミット 18-0）

旧コードのまま、いまの挙動を固定するテストを先に足す（失敗しないテスト）。テストが無い経路：

  • 作り直されたファイルが、作り直し後は別プロジェクト／空になる → 一覧から消える（A2 ④）
  • 1 回の Refresh で「取り込み済み → Hook に切り替え」と「Hook の追記」が同時に来る
  • 読み込み中の IOException（ロック）→ ログに出し、次回に読み直す

6. 問題なしと判断した所
